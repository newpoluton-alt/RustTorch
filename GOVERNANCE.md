# Governance

RustTorch is currently maintained by [@newpoluton-alt](https://github.com/newpoluton-alt).
This document describes the present single-maintainer project; it does not imply
an organization or committee that does not exist.

## Roles

Contributors propose changes, provide evidence, participate constructively in
review, and follow the contribution and conduct policies. Repeated contribution
does not by itself grant repository access.

Maintainers triage work, review and merge changes, enforce project policy,
manage compatibility scope, coordinate security work, authorize releases, and
administer repository settings. Maintainer access is a responsibility, not a
rank or employment relationship.

## Decisions

Technical decisions seek consensus through issues and pull requests. Evidence,
maintainability, compatibility, safety, and current project scope outweigh vote
counts. The current maintainer makes the final decision when consensus is not
possible and records material rationale publicly unless a security embargo
prevents disclosure.

Anyone participating in a decision must disclose a relevant financial,
employment, personal, or project conflict. A conflicted maintainer should avoid
sole review when an informed independent reviewer is available. With only one
maintainer, the conflict and reasoning are recorded and external review is
sought where practical.

## Security and releases

The maintainer controls vulnerability-report access, embargo scope,
coordination, and disclosure timing under the security policy. Only a
maintainer may authorize a version, crates.io publication, Git tag, or GitHub
release. Release authority does not permit bypassing required version,
changelog, compatibility, package, or provenance checks.

## Adding or removing maintainers

A future maintainer should demonstrate sustained high-quality contributions,
sound review judgment, respect for compatibility and security boundaries,
reliable policy enforcement, and adherence to the Code of Conduct. The current
maintainer appoints new maintainers through a public governance change that
states scope and repository access.

Maintainers may resign at any time. Access may be removed for inactivity,
unresolved conflicts, security risk, policy violations, or conduct violations;
the public explanation must avoid disclosing embargoed or sensitive details.
If the sole maintainer becomes unavailable, contributors may fork the project,
but no contributor can assume control of the original repository without the
hosting platform owner's authorization.

Governance changes use an issue and reviewed pull request. See the
[maintainer guide](docs/maintainer-guide.md) for operational practice.
